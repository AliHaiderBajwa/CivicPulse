[1] F4 - triage content-hash cache hit rate, measured (rubric F4)

$ python scripts/triage_hit_rate.py --base-url http://127.0.0.1:8912 \
      --uniques 10 --repeats 4
{
  "nonce": "d9de79aa",
  "posts": 40,
  "post_statuses": [201],
  "uniques": 10, "repeats": 4,
  "cache_hits": 30, "cache_misses": 10, "cache_lookups": 40,
  "hit_rate": 0.75, "expected_hit_rate": 0.75,
  "fallbacks_during_run": 0,
  "all_201": true
}
exit=0

Reproducibility (second consecutive run, nonce de181517): identical
30 hits / 10 misses / hit_rate 0.75 / exit=0.

Why exactly 75%: content_key = "triage:v1:{provider}:{sha256(normalised text)}"
(backend/app/services/triage_orchestrator.py:26) - the first copy of each of
the 10 distinct texts is a miss, each of the 3 repeats is a hit, so
expected = (4-1)/4 = 0.75. The script rotates X-Forwarded-For per POST so the
10/min/client limiter never returns a 429 (report shows all_201=true), and it
fails (exit 1) unless hits == uniques*(repeats-1), misses == uniques, and the
fallback counter did not move. Counter deltas are read from GET /metrics
(triage_cache_total{result="hit"|"miss"}).

[4] /metrics is not routed through the rate limiter

Same client (X-Forwarded-For: 9.9.9.9), 12 rapid POST /api/complaints:
201,201,201,201,201,201,201,201,201,201,429,429
=> the PDF's 10/minute per client kicks in on POST (11th/12th rejected).

$ GET /metrics  (immediately after those two 429s)  -> HTTP 200
=> the limiter is a dependency of the complaints router only; /metrics is
   served regardless of a client having exhausted quota.

--------------------------------------------------------------------------------
[5] /metrics does not touch Postgres

Runtime proof: boot healthy, then `docker stop cp-pg` under the running app:

GET /health  -> 200                      (liveness: never DB-dependent)
GET /ready   -> 503 {"status":"degraded","dependencies":{"postgres":false,
                     "redis":true}}      (readiness takes the hit)
GET /metrics -> 200
   series live while DB is down:
   http_requests_total{method="GET",path="/health",status="200"} 2.0
   http_requests_total{method="GET",path="/ready",status="503"} 1.0
docker start cp-pg -> GET /ready 200     (recovery, no restart needed)

Documented behaviour change from the lifespan migration (PR #25 review):
BOOTING with an unreachable database now fails fast - alembic upgrade head
raises, uvicorn logs "Application startup failed. Exiting." and exits non-zero.
That is the sanctioned semantics (Ali's review: "transactional DDL means the
loser aborts and succeeds on restart" - orchestrators restart until the DB is
there; cd.yml waits for sts/postgres before the app starts). The degraded-
serving evidence in evidence/25 [11] remains valid for RUNTIME database death,
reproduced above.
