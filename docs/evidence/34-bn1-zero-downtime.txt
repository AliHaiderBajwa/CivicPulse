# Evidence 34 — BN1: zero-downtime rolling update under live load

Captured 2026-09-27T11:26:41Z by Ali Haider Bajwa. All numbers below are
k6's own end-of-run summary (`/tmp/bn1-summary.json` + `bn1.log`), quoted
verbatim; the procedure is reproducible via `scripts/load/rolling-update.js`.

## Procedure

1. Constant load: 15 VUs × 150 s against the k3d Ingress
   (`http://127.0.0.1:8080`, `Host: civicpulse.localhost` — same routing
   as the `k8s-up.sh` smoke). Every iteration POSTs a complaint (unique
   `X-Forwarded-For` per request so the per-IP limiter never trips) and
   GETs `/api/stats`. HPA left ENABLED throughout.
2. At T+50 s into the run: `kubectl rollout restart deployment/backend`.
   Rollout completed DURING the run (`successfully rolled out`); rollout
   history advanced (revisions 1–4, the test restart creating the newest).
3. Deployment strategy (pre-existing, no manifest changes for this test):
   `RollingUpdate` with `maxSurge: 1, maxUnavailable: 0` — a replacement
   pod must be Ready before any old pod terminates.
